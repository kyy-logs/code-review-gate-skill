# probe: behavior-review（行为正确性）

**required: true** ｜ **requires: []**

检查本次改动引入或触发的行为缺陷。审查范围和源码版本以 `SKILL.md` 的“确定审查范围”为准；
不依赖规则包，也不受规则扫描的语言扩展名限制。
按需追踪实际调用链，不受 `impact-analysis` 的一层 fan-in 限制；未找到调用方不能单独证明内部逻辑正确或错误。

## 1. 取证方法

从 diff 列出变化的行为入口或分支（位置及分支，不预设缺陷），按相关状态或对象组织行为链。逐条完成以下取证和判断；关联分支一起推演、复用已读证据，不同触发条件与后果分别判断。发现问题后继续检查其余变化路径，不因同函数或同根因已有 finding 就停止。

1. 先读取项目内相关入口与实现，确认实际调用的完整方法签名、已有契约和本次变化；不能用同名重载或相似接口代替。
2. 涉及状态变化时，检索本次改动影响的状态字段的相关直接读写及包装方法（含回调），串起“状态写入 → 守卫判断 → 后续执行”，再对照变更前后的触发条件与副作用。不能用某个 getter 无调用方或关联实现未修改，代替这条链的核对。
3. 仅针对当前链中可能改变判断的具体证据缺口，沿实际调用链补读相关方法、契约或测试；补读前明确待核实的问题。对决定结论的库或框架调用，核对目标版本的接口声明、方法契约或实现，不凭方法名推断返回值和异常。涉及模型或缓存读取时，沿对象获取、创建和包装路径，核对实际返回实现及相关覆写方法；不能仅按接口字段、方法名或默认实现推断行为。
4. 本条链形成“确认问题”“有依据地排除”或“未验证及具体缺口”的判断后，转入下一条；排除须写明依据，不能把未验证当作排除。仅在新证据或具体反例可能改变结论时回查已判断的链，并复用已有证据。

预期依据可来自接口契约、设计、已有测试或明确的代码不变量，不得自行编造业务规则。

## 2. 行为检查

对本次改动影响的主要路径，结合入口、调用方和上下文检查：

- 条件分支是否符合预期，是否存在判断反向或遗漏分支；路由变化时，对照同一输入在变更前后的实际路径，将新路径触发的既有缺陷纳入本轮检查。
- 状态转换是否允许，副作用是否在正确条件下执行。
- 空值、空集合和数值边界是否处理正确。
- 异常或部分失败后，状态与资源是否正确处理。

结合行为链选择适用的检查方向、具体反例并推演：

- **解析 / 校验**：先确认输入语言和依赖版本，主动补读相应语法或格式契约，不能只用当前样例代表合法输入。依据契约选择合法的等价写法，沿“解析 → 校验 → 使用”核对结果是否一致，是否绕过校验。
- **序列化 / 模板渲染**：沿调用链补读实际包装、渲染和解析实现，并对照相关旧入口。沿实际转换顺序追踪变量值，选择引号、反斜杠或换行等相关输入，核对转义、解码是否改变原值或破坏结构。

**并发与异步检查矩阵**：涉及共享状态、重试或异步任务时，按本次改动的代码信号选择适用行；同一行为链可适用多行。

| 类型及代码信号 | 要推演的交错或顺序 | 排除问题时需核对的保证 |
| --- | --- | --- |
| 检查后执行：先查缓存、状态或存在性，再操作 | 检查与操作之间，其他执行者改变状态，原执行者仍按旧结果操作；包括无锁访问和跨临界区操作 | 在同一临界区内检查并执行或重检，或有等效原子协议；单次读写加锁不足以证明整体原子 |
| 读改写：读取旧值，计算后写回 | 两个执行者读取同一旧值，后写覆盖先写，丢失更新 | 整个读改写由锁、原子操作或符合所需隔离语义的事务保护 |
| 可见性与发布：跨线程初始化对象或更新就绪标志 | 读取方观察到就绪标志，却看不到完整或最新数据 | 实际读写之间存在有效的发布与可见性保证，或状态只由同一线程访问 |
| 取消与任务结束：完成、异常或取消回调释放 busy/loading | 状态已释放，原任务及子任务仍运行，新任务获准进入 | 按项目契约分别核对完成、异常、取消的收尾顺序、重入守卫及任务隔离；取消通知不等于任务结束 |
| 过期回调：新旧任务共用状态或结果 | 旧任务晚到的完成、异常或取消回调覆盖或清空新任务状态 | 回调校验任务身份或版本，或有实际顺序及隔离保证 |
| 重复执行：重试、重复消息或重复触发产生副作用 | 两次执行都通过检查，重复执行本应只发生一次的操作 | 原子占用、去重或幂等机制满足业务契约；判断幂等须覆盖状态写入及外部可观察副作用，不能仅凭计算结果相同排除问题；项目契约允许重复时不据此建项 |
| 死锁：多把锁，或持锁调用其他组件、回调 | 不同路径反向获取锁，或互相等待对方完成 | 统一锁顺序、避免持锁等待，或其他能阻止等待环的实际保证 |

对适用项，找到实际线程、任务或回调入口及相关读写、锁位置。对操作竞争给出具体交错和状态变化；对可见性与发布问题，说明相关读写及同步、发布依据。排除须指出阻止该顺序或后果的保证，不能只写“有锁”或“分支互斥”。证据不足时按第 1 节记录具体缺口，不当作已排除。不要求穷举线程组合、强行建项或输出整张矩阵；复用现有证据和“实际检查范围”。

其他行为变更按主要路径另选反例。

## 3. 记录与上报

检查记录统一说明：
**处理点位置 → 触发条件及具体输入 → 预期行为及依据 → 相关代码路径 → 实际行为与后果**。

主要路径均已有上述判断后，复用记录整理并写入探针 JSON；收尾时不例行扩展依赖或重查已判断的路径。若发现可能改变结论的新证据、具体反例或证据矛盾，再回到对应链取证。
返回消息沿用“实际检查范围”，按路径简述已检查、未验证及具体缺口后结束，不新增字段或报告区域。

已确认问题写入 finding 的 `evidence`；定级及契约冲突处理统一遵循 [输出契约](../output-schema.md)。
不同根因或不同后果分别记录，不得合并以规避定级；依赖未消解契约冲突的问题即使不建 finding，也须单列为未验证项。
语法依据、实际实现链路或合法触发输入的可达性未核实时，注明具体缺口，不得当作已证实缺陷。
未完成或证据不足的检查列为未验证项及限制，不得笼统记为“已检查”；未运行时标明“静态推演”，不得称为已复现。

行为 finding 不要求已有规则 ID，也不受 `repo-guard` 仅报告 HIGH 级别规则的限制。
