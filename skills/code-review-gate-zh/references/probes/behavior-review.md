# probe: behavior-review（行为正确性）

**required: true** ｜ **requires: []**

先读 [`common.md`](common.md)；它定义了所有探针共同遵守的约束。

检查本次改动引入或触发的行为缺陷。审查范围和源码版本以 `SKILL.md` 的“确定审查范围”为准；
不依赖规则包，也不受规则扫描的语言扩展名限制。
按需追踪实际调用链，不受 `impact-analysis` 的一层 fan-in 限制；未找到调用方不能单独证明内部逻辑正确或错误。

## 1. 取证方法

从 diff 找出变化的行为入口或分支，按相关状态或对象组织行为链，逐条取证并判断。关联分支复用证据，不同触发条件与后果分别判断；发现问题后继续检查其余变化路径。引用具体源码位置，不预设缺陷或编造业务规则。

1. **确认变化**：读取相关入口与实现，确认实际调用的方法签名、已有契约及变更前后的行为。预期依据可来自接口契约、设计、测试或明确的代码不变量。涉及校验范围、默认值或分支变化时，分别核对新增接受或拒绝的输入是否符合变更意图，不能仅凭实现已改变就认定旧测试过时；依据冲突未解决时，记录具体冲突。
2. **追踪状态链**：先确认本次改动涉及的关键状态的契约及读取用途，再对各个写入入口追踪“入口 → 状态读写 → 守卫 → 后续动作”，比较触发时机，分别判断状态写入、后续准入和副作用是否符合契约。共用包装方法的完成、异常、取消入口分别判断，不能相互替代。涉及并发或异步时，核对实际执行线程、调度边界、回调同步或排队及任务结束顺序。状态契约无法确定时，按输出契约将具体争议写入 `unverified_items`。
3. **按疑点补证**：仅为可能改变判断的具体缺口补读，先明确待核实的问题及可能的证据来源。决定结论的库或框架调用须核对目标版本的声明、契约或实现；模型、缓存读取须沿对象获取和包装路径确认实际实现及相关覆写，不能凭方法名、同名重载或默认实现推断。仅在有具体历史线索且可能改变判断时查 Git 历史。契约冲突无法消解且无新线索时，停止补证，按输出契约记为未验证，列明双方依据及不同解释下的行为后果；不得仅采信其中一方作排除结论。
4. **完成判断**：各路径分别记录“确认问题”“有依据地排除”或“未验证及具体缺口”。排除结论只覆盖证据已验证的后果；同一路径中的其他契约、状态含义和准入条件须分别判断，不能因一种风险不成立就排除整条路径。未验证须说明缺口影响触发、顺序或后果的哪一步。区分“给定实现支持路径”与“目标构建版本已确认”；版本缺口决定可达性时保留为未验证，不笼统否定已有证据。完成一条链后转入下一条，仅在新证据或具体反例可能改变结论时回查。

## 2. 行为检查

对本次改动影响的主要路径，结合入口、调用方和上下文检查：

- 条件分支是否符合预期，是否存在判断反向或遗漏分支；路由变化时，对照同一输入在变更前后的实际路径，将新路径触发的既有缺陷纳入本轮检查。
- 状态转换是否允许，副作用是否在正确条件下执行。
- 空值、空集合和数值边界是否处理正确。
- 异常或部分失败后，状态与资源是否正确处理；涉及数据库、缓存、消息或外部调用的连续操作时，核对部分成功、超时及重试后，是否出现契约不允许的状态不一致或重复副作用。

结合行为链选择适用的检查方向、具体反例并推演：

- **解析 / 校验**：先确认输入语言和依赖版本，主动补读相应语法或格式契约，不能只用当前样例代表合法输入。依据契约选择合法的等价写法，沿“解析 → 校验 → 使用”核对结果是否一致，是否绕过校验。
- **序列化 / 模板渲染**：沿调用链补读实际包装、渲染和解析实现，并对照相关旧入口。沿实际转换顺序追踪变量值，选择引号、反斜杠或换行等相关输入，核对转义、解码是否改变原值或破坏结构。

**并发与异步检查矩阵**：涉及共享状态、重试或异步任务时，按本次改动的代码信号选择适用行；同一行为链可适用多行。

按适用类型读取[交错轨迹示例](../concurrency-examples.md)，将执行者、状态和交错位置映射到实际源码，核对路径可达性及保护机制；不直接套用示例结论。

| 类型及代码信号 | 核心风险 | 排除依据 |
| --- | --- | --- |
| 检查后执行：先查缓存、状态或存在性，再操作 | 操作前状态改变，包括两个临界区之间的变化 | 原子协议保证操作前提仍成立；重检其他状态须能保证该前提；单次访问加锁不足 |
| 读改写：读取、计算、写回 | 并发更新相互覆盖 | 锁、原子操作或具有所需隔离语义的事务保护整个操作 |
| 可见性与发布：跨线程初始化或就绪标志 | 标志已就绪，数据却不完整或陈旧 | 有效的发布与可见性保证，或状态限于单线程 |
| 取消与任务结束：回调释放 busy/loading | 原任务或子任务仍运行，新任务已获准进入 | 分别核对状态查询契约、收尾顺序与新任务准入；结果隔离只排除结果覆盖，不能单独证明 busy/loading 可释放；取消通知不等于任务结束 |
| 过期回调：新旧任务共用状态 | 旧回调覆盖或清空新任务状态 | 任务身份或版本校验，或有效的顺序与隔离保证 |
| 重复执行：重试、重复消息或触发 | 本应只执行一次的操作重复发生 | 原子占用、去重或幂等覆盖状态及可观察副作用；结果相同不足以证明幂等；契约允许的重复不算缺陷 |
| 死锁：多把锁或持锁调用 | 反向获取锁或循环等待 | 锁顺序、避免持锁等待，或其他阻止等待环的保证 |

对操作竞争给出具体交错和状态变化；对可见性与发布问题说明同步、发布依据。取证与判断沿用第 1 节。不要求穷举线程组合、强行建项或输出整张矩阵；复用现有“实际检查范围”。

其他行为变更按主要路径另选反例。

## 3. 记录与上报

检查记录统一说明：
**处理点位置 → 触发条件及具体输入 → 预期行为及依据 → 相关代码路径 → 实际行为与后果**。

主要路径均已有上述判断后，复用记录整理并写入探针 JSON；收尾时不例行扩展依赖或重查已判断的路径。若发现可能改变结论的新证据、具体反例或证据矛盾，再回到对应链取证。

已确认问题写入 finding 的 `evidence`；定级及契约冲突处理统一遵循 [输出契约](../output-schema.md)。
不同根因或不同后果分别记录，不得合并以规避定级；依赖未消解契约冲突的问题，未建 finding 时须写入 `unverified_items`。
语法依据、实际实现链路或合法触发输入的可达性未核实时，注明具体缺口，不得当作已证实缺陷。
未完成或证据不足的检查列为未验证项及限制，不得笼统记为“已检查”；未运行时标明“静态推演”，不得称为已复现。

行为 finding 不要求已有规则 ID，也不受 `repo-guard` 仅报告 HIGH 级别规则的限制。
